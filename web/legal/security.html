1. Approach

The hosted service holds business data that our customers did not choose to publish and did not choose to hand to a third party. We treat it that way. The controls below are the ones we actually implement and test, not a wish list.

Reporting a vulnerability? Please read section 12 first. We will not pursue legal action for good-faith research that respects customer data and the privacy of other users.

2. Tenant isolation

Every account belongs to a tenant, and every tenant's data tables live in a dedicated DuckDB schema (analytics_t_<tenant>) inside the warehouse. A query written without a schema qualifier resolves inside the caller's own schema, so the application's own code path cannot read another tenant's tables.

Because DuckDB has no per-session schema permissions, there is a second layer: the SQL surface refuses any reference to another tenant's schema and to the system catalogues, and identifiers taken from a request are validated against a strict pattern before they reach SQL. The tenant schema name embeds a hash of the tenant identifier, so it cannot be enumerated either.

Raw uploads are written to a directory per tenant. A deployment that must defend against a hostile database client rather than a hostile query can run each tenant in its own warehouse file; that mode is described in the operations documentation.

Isolation is enforced by automated tests that fail the build if a tenant can read, write, list or drop another tenant's table.

3. Encryption and key management

  • In transit — TLS 1.2 or higher for every connection to the application and to the model provider.
  • At rest — the hosting and storage providers encrypt volumes and objects at rest.
  • Application keys — the session-signing key and the entitlement-signing key are generated locally, stored outside the data tree, and never written to logs, exports or routine backups. A hosted deployment can point the entitlement key at an external authority so that the signing material never sits beside the data.
  • Credentials in code — no secret is committed to the repository. The release build excludes credential files and self-checks the archive it produced.

4. Identity and access management

  • Passwords are stored as salted bcrypt hashes, never in plain text and never recoverable.
  • Sessions are signed and expire; a revoked token is rejected for the remainder of its life.
  • Access control is role-based with a deny-by-default model for mutating operations: a route that is not explicitly granted requires a permission the caller's role does not hold.
  • Multi-factor authentication is available and required for administrator accounts in hosted deployments.
  • The first account created on a network-reachable instance must present a bootstrap token, so a fresh deployment cannot be taken over by whoever registers first. A loopback-only desktop install is exempt.
  • Administrative actions — role changes, account deletion, plan changes — are recorded in the audit trail.

6. Platform and infrastructure

  • The service runs behind a reverse proxy or load balancer that enforces a Host allow-list, so a forged Host header cannot reach the application.
  • Proxy headers are only trusted from networks on an explicit allow-list; otherwise every client behind the proxy would share one rate-limit bucket.
  • Headers are set on every response: a strict content security policy, the frame options, the content type options, and the referrer policy. Static legal and UI pages ship no external scripts, styles, fonts or images, so the policy does not need to be relaxed for them.
  • The application server runs as a non-privileged user with no write access outside its data directory.

7. Audit trail

Security-relevant actions — sign-in, sign-out, failed sign-in, role change, account deletion, data export, query execution, entitlement change — are recorded with a timestamp, the acting user, the tenant, the resource, the action and the outcome.

The default sink is a local file, which is appropriate for a single-process install. A hosted deployment points the sink at a shared, durable backend (Redis or SQLite) so the trail survives the replacement of a container and is consistent across replicas. A sink failure degrades to "the event was not recorded"; it never fails the request that caused it.

8. Monitoring and metrics

The service exposes a Prometheus-format metrics endpoint and a deep health endpoint that probes each dependency individually.

  • Metricsrequest counts and latency by normalised route, query outcomes, assistant usage by feature, rate-limit refusals by bucket, row counts, and the number of tenants.
  • Deep healththe API process, the warehouse (readable and writable), the identity store, the audit sink, the model provider, the billing service, and the local model server, each with a boolean and a short reason.
  • Livenessprocess-only, so a slow dependency never causes the process to be killed and restarted.
  • Readinessthe warehouse has to be usable before traffic is routed to the instance.

Metrics never contain a customer identifier: routes are normalised so that an identifier cannot create a new time series, and a tenant is represented by a hash of its identifier rather than by the identifier itself.

9. Incident response

On becoming aware of a security incident or a personal data breach, we:

  1. contain it — revoke credentials, disable the affected feature or stop the affected instance;
  2. preserve the evidence — logs, audit records and a snapshot of the affected data are secured before anything is changed;
  3. assess it — what data was affected, which tenants, and whether personal data was involved;
  4. notify — affected customers without undue delay and within 48 hours of confirmation, and the supervisory authority where the law requires it;
  5. remediate — fix the root cause, not only the symptom, and add a regression test that fails without the fix.

Customers are told what happened in plain language, what data was involved, what we have done and what we need them to do.

10. Vulnerability management

  • Dependencies are pinned and reviewed; a release build never pulls an unpinned package at install time.
  • Automated static analysis and a dependency vulnerability scan run on every change.
  • Any change that touches authentication, authorisation, payments, SQL or user input requires a security review before it is merged, and the invariants it relies on are covered by regression tests that fail if the behaviour regresses.
  • Findings are triaged by severity and exploitability, and a remediation window is set accordingly.

11. Backup and resilience

The warehouse, the identity store, the configuration and the raw uploads are backed up on a schedule. The backup tool takes a consistent snapshot of the warehouse without competing with the running application's writer, verifies every file against a manifest of hashes, and refuses to restore over a live installation without an explicit confirmation.

Backup archives exclude credential material by default. A restore drill is run on a schedule so that a backup is known to be restorable, not merely known to exist. The full procedure is described in the backup and restore documentation.

13. Reporting a vulnerability

If you believe you have found a vulnerability, email [[SECURITY_EMAIL]] with a description, the steps to reproduce it and the impact you believe it has. Please do not access data that is not yours, do not degrade the service for other users, and do not use social engineering against our staff.

We acknowledge reports within two business days, keep you informed while we investigate, and credit you in the release notes if you would like us to.
